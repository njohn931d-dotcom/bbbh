I built a small site of money calculators — you type in a price and it tells you how many hours of your working life it costs. Side project, no team, no deadline.

The obvious 2026 move is Next.js, a database, an auth provider and a component library. I went the other way, and the reason is boring: every page on that site is a static HTML file generated by one Node script, and the entire client-side footprint is **32 KB of JS and CSS combined**.

Here is the shape of it, and the parts that were worse than I expected.

## What is actually deployed

- 87 pre-rendered HTML pages (a home page, 47 calculator/guide routes, plus article mirrors)
- 32 KB of JS + CSS total, ~6.5 KB gzipped per page
- 1.8 MB for the whole built site, including every page
- GitHub Pages as the host, no server process anywhere

Those numbers are measured from the production build, not aspirational: `find dist -name 'index.html' | wc -l`, and `du -ch dist/assets/*`.

## Why static HTML instead of a client-side router

Three reasons, in the order they mattered to me:

1. **Each URL is a real document.** Unique `<title>`, meta description, canonical URL and breadcrumbs are in the HTML the server sends, before any JavaScript runs. If a crawler or a link preview fetcher never executes my JS, the page still describes itself correctly.
2. **No hydration cost.** There is nothing to hydrate. The calculator is a form and a handful of DOM updates.
3. **Deploying is copying files.** There is no runtime to keep alive, no cold start, no server bill.

If your app is behind a login and half of it depends on live data, none of this applies. For a tool page where the "backend" is arithmetic, it does.

## The generator is a for-loop

Stripped to the essential part, the build is this:

```js
const routes = [...baseRoutes, ...articleRoutes]; // 47 routes

for (const route of routes) {
  const html = renderRoute(route); // title, description, canonical, JSON-LD, body
  fs.mkdirSync(route, { recursive: true });
  fs.writeFileSync(`${route}/index.html`, html);
}

fs.writeFileSync('public/sitemap.xml', renderSitemap(routes));
fs.writeFileSync('public/robots.txt', renderRobots(siteUrl));
```

The real file is ~950 lines, and honestly ~800 of those are content, not code. The loop has not changed since the first version.

Two details that carry their weight:

**One origin constant.** Everything — canonical URLs, the sitemap, internal links, the LLM index — is derived from a single `SITE_URL`. Get that wrong and you ship a production site where all 87 pages confidently claim to live somewhere else. A test now asserts the canonical URL of every generated page equals `SITE_URL + path`, which is the cheapest bug I ever prevented.

**Generated output is not committed.** Route directories, `sitemap.xml`, `robots.txt` and the article mirrors are all in `.gitignore`. The build produces them. If a generated file is in your diff, you are one merge conflict away from shipping something stale that nobody can explain.

## The calculator itself

The whole tool is one `app.js` with three modes configured as data:

```js
const configs = {
  purchase:     { title: 'Is it worth your time?',  label: 'How much does it cost?' },
  subscription: { title: 'Small monthly. Big yearly.', label: 'Monthly subscription cost' },
  saving:       { title: 'Little habits. More possibility.', label: 'Daily amount to set aside' },
};
```

A route is static HTML plus the mode it should boot into. Adding "car loan" instead of "cost per wear" is a config entry and a route, not a new component tree. That is the entire reason the site can carry dozens of near-identical tools without the codebase collapsing into `if` statements.

## What I would do differently

**Keep content out of the generator.** Right now the article copy lives inside the build script. It works, and it is miserable to diff. If I were doing it again, the content would be markdown files and the generator would stay under 200 lines.

**Near-duplicate pages are a real cost.** Dozens of pages built from one template with one paragraph swapped is the definition of thin content. Mine differ in metadata, worked examples and FAQ answers, but I would not claim that is automatically enough — it is a structural risk I accepted knowingly, not a solved problem.

**Tests on generated output pay for themselves immediately.** The suite that walks every URL, parses the HTML and asserts canonical/title/description uniqueness caught real breakage within the first hour of existing.
